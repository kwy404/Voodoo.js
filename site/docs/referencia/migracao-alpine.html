Quality and migration

Migrating from Alpine

Both start from the same idea: behavior declared in the HTML, with no build step. The conversion is usually almost mechanical. The real differences show up in what Voodoo brings along, which in Alpine lives in plugins or in your own code.

On v-model: .lazy, .number and .debounce exist in both, here the debounce time comes from the v-debounce attribute. .throttle does not exist; .trim and .single, for files, are new.

Magic variables

$el, $refs, $store, $watch, $dispatch, $nextTick, $root, $data and $event are the same. $id becomes V.uid(), and the plugin's $persist becomes the v-persist directive.

These do not exist in Alpine: $parent, $self, $detail, $http, $toast, $modal, $form, $storage, $cookie, $url, $cache, $screen, $network, $device, $theme, $clipboard, $route, $router, $t and $locale.

Store and global data

// Alpine
Alpine.store('cart', { items: [], add(p) { this.items.push(p) } });

// Voodoo.js
V.store('cart', { items: [], add(p) { this.items.push(p) } });
V.store('cart', { items: [] }, { persist: true });   // persistence at creation time

In the HTML, both use $store.cart.

// Alpine: Alpine.data
Alpine.data('dropdown', () => ({ open: false, toggle() { this.open = !this.open } }));

// Voodoo.js: a component
V.component('dropdown', {
  state: () => ({ open: false }),
  methods: { toggle() { this.open = !this.open } }
});

Directives, magic variables and plugins

// Alpine
Alpine.directive('highlight', (el, { expression }, { evaluate }) => {
  el.style.background = evaluate(expression);
});
Alpine.magic('now', () => new Date());
Alpine.plugin(myPlugin);

// Voodoo.js
V.directive('highlight', (el, binding) => { el.style.background = binding.value });
V.magic('$now', () => new Date());
V.use(myPlugin, { option: true });

Initialization

<script src="voodoo.min.js?v=0.6.2" data-manual></script>
<script>
  V.component('x', { /* ... */ });
  V.start();
</script>

With the plain tag, V.start() is called on its own, use data-manual when you want to register everything first. The event equivalent to alpine:init is voodoo:ready, fired after mounting.

Three differences worth your attention

1. Interpolation with a single brace

<!-- Alpine -->
<span x-text="name"></span>

<!-- Voodoo -->
<span>{ name }</span>

2. The attributes disappear from the HTML

Once processed, the directive leaves the document. If you have CSS or scripts that depend on selectors like [x-show], adapt them to use classes, or turn the cleanup off with V.config.cleanAttributes = false.

3. v-if does not need a template

<!-- Alpine -->
<template x-if="loggedIn"><p>Welcome</p></template>

<!-- Voodoo -->
<p v-if="loggedIn">Welcome</p>

What you gain in the switch

  • declarative requests: v-get, v-post, v-resource, v-poll, v-search;
  • a complete AJAX form with v-submit, validation, masks, upload and autosave;
  • UI: modal, drawer, tabs, dropdown, tooltip, accordion, command palette;
  • notifications and dialogs that return a promise;
  • accessible drag and drop;
  • storage, cookies, cache and the query string;
  • in the full build: charts, spring animations, router, languages and the inspector.

What you lose

  • Alpine's plugin ecosystem, which is larger and older;
  • x-modelable, which here becomes props with emit;
  • the utility-class syntax right inside x-transition;
  • the .camel and .dot modifiers of x-bind;
  • and a few kilobytes: Alpine is smaller because it does less.
Gradual migration

The two libraries use different prefixes, so they live side by side on the same page without colliding. Migrate screen by screen, swapping x- for v-, and remove Alpine once none are left.
